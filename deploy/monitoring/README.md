# Monitoring: Prometheus + Grafana (v3.20)

Self-hosted, all open source, no paid tier anywhere: Prometheus, Grafana OSS,
node_exporter, cAdvisor, postgres_exporter, and `prom-client` inside the API.
Everything runs on the same VPS as the products, in its own compose project
(`techpioasset-monitoring`), and watches **both** products on the host.

## What you get

| Dashboard     | Shows                                                                                                |
| ------------- | ---------------------------------------------------------------------------------------------------- |
| Host          | CPU, memory, disk space, disk I/O, load, swap, uptime                                                |
| Containers    | CPU / memory / network per container, restarts in the last 24 h (every container, both products)     |
| PioAssets API | requests, latency p50/p95/p99, 5xx and 429 rates by route; Node memory / CPU / event loop; the fleet |
| Postgres      | connections, transactions, cache hit, size, longest transaction, temp files (production and staging) |

"The fleet" is the API counting its own data once a minute: companies, agents
online / offline / needs reinstall, refresh requests pending, assets by status,
Microsoft 365 connections by last sync result. These never existed as numbers
before; they are what tells you the laptops stopped talking before a user does.

Ten alert rules are provisioned (`grafana/provisioning/alerting/alerts.yml`):
API unreachable, 5xx above 2 %, p95 above 2 s, disk under 15 % free, memory
under 10 % available, production database unreachable or near its connection
limit, fleet counts stale, every agent offline at once, a container restarting
repeatedly. They show under Grafana → Alerting whether or not email is set up.

## Setting it up (one command)

```bash
ssh root@<vps> /opt/techpioasset/deploy/monitoring/setup.sh
```

Then put Grafana behind nginx on the main site: add this line inside the
`pioassets.com` TLS server block, just before `location / {`, and reload.

```bash
ssh root@<vps> 'sed -i "/^    location \/health\/ {/i \    include /opt/techpioasset/deploy/nginx/grafana.location.conf;" /etc/nginx/sites-enabled/pioassets.com && nginx -t && systemctl reload nginx'
```

Open `https://pioassets.com/grafana/`, sign in as `admin` with the
`GRAFANA_ADMIN_PASSWORD` line from `/opt/techpioasset/deploy/monitoring/.env.monitoring`,
and change it under the profile menu on first login.

`setup.sh` is safe to run again: it keeps an existing `.env.monitoring`,
re-applies the database roles, and restarts only what changed.

## Alert email

Alerts reach nobody until SMTP is configured. In `.env.monitoring` set
`ALERT_EMAIL`, `GRAFANA_SMTP_ENABLED=true`, `GRAFANA_SMTP_HOST`
(`host:port`), `GRAFANA_SMTP_USER`, `GRAFANA_SMTP_PASSWORD`, `GRAFANA_SMTP_FROM`,
then:

```bash
cd /opt/techpioasset/deploy/monitoring && docker compose -f docker-compose.monitoring.yml --env-file .env.monitoring up -d grafana
```

Grafana → Alerting → Contact points → `ops-email` → **Test** sends a test mail.
A Microsoft Teams or Slack webhook can be added as a second contact point in
the UI; the provisioned one is email because every office has an inbox.

## Security

- Grafana and Prometheus bind to `127.0.0.1` only. Grafana is reachable solely
  through nginx with TLS and its own login; sign-up and anonymous access are
  off; Prometheus is not exposed at all (SSH tunnel: `ssh -L 9090:127.0.0.1:9090 root@<vps>`).
- The exporters publish no ports. Prometheus reaches them over the private
  `monitoring` network, and reaches each API's metrics port (9464) over the
  application networks it joins. That port is **never** in a `ports:` list, so
  the per-company counts cannot be read from the internet. The main API has no
  `/metrics` route (pinned by `apps/api/test/metrics.integration.test.ts`).
- The database role is `pg_monitor` only: statistics views, never table rows,
  `NOBYPASSRLS`.
- No telemetry: Grafana's update checks, usage reporting and news feed are off.
- Grafana is one more login on the internet. Keep the admin password in the env
  file only, and add it to the fail2ban jail list when that is set up.

## Limits to know

- **A monitor on the VPS cannot see the VPS down.** Keep an outside uptime
  check on `https://pioassets.com/health/ready` as well.
- Host network counters are not collected (from inside a bridge network they
  would describe the container); per-container network is on the Containers
  dashboard.
- Retention is 30 days or 4 GB, whichever comes first.
- Dashboards are provisioned read-only from `grafana/dashboards/*.json`,
  generated by `grafana/build-dashboards.py`. Edit the Python, rerun it, commit
  both; Grafana picks up the change within a minute. To experiment in the UI,
  "Save as" a copy.

## Day to day

```bash
# are all targets being scraped?
curl -s http://127.0.0.1:9090/api/v1/targets | grep -o '"health":"[a-z]*"' | sort | uniq -c
# reload prometheus.yml after an edit
curl -s -X POST http://127.0.0.1:9090/-/reload
# logs
docker compose -f /opt/techpioasset/deploy/monitoring/docker-compose.monitoring.yml --env-file /opt/techpioasset/deploy/monitoring/.env.monitoring logs --tail 50
```

The API side lives in `apps/api/src/observability/metrics.ts`; `METRICS_PORT=0`
turns the listener off, which the test lanes do.

## Notes from the first rollout (4 Nov 2026)

- Grafana validates the SMTP from-address and the email contact point even
  with SMTP off, so the compose file defaults them to `monitoring@<host>` and
  `nobody@<host>`. Replace `ALERT_EMAIL` with a real inbox when you set up SMTP.
- cAdvisor must be v0.55 or newer on this VPS: Docker 29 keeps images in the
  containerd store, and v0.52 registered no containers at all.
- The whole stack measured about 215 MB of RAM with every container running.
